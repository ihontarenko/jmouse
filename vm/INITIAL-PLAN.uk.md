**Напрям підтримую. Основу я б будував як розширюваний компілятор зі збереженням семантики Java.** Власний AST і читабельний TypeScript добре поєднуються, але між ними потрібні явні етапи розв’язання символів, аналізу залежностей і перетворення мовних конструкцій.

Прочитав інструкції `.claude` та скілл `java-architecture`. Переглянув наявні модулі й основні вузли TeaVM. Нижче — початковий архітектурний план; код не змінював.

### 1. Спочатку зафіксувати межі та термінологію

Маємо розрізняти:

- **Java AST** — що написано у вихідному коді.
- **Семантичну модель** — що означають типи, вирази, виклики та посилання.
- **Lowering** — перетворення конструкцій Java на конструкції, які може реалізувати цільова платформа.
- **Цільовий AST** — структура майбутнього TypeScript.
- **Writing** — запис цільового AST у читабельний текст.

Це дозволить змінювати вигляд TypeScript окремо від правил поведінки Java.

«Java to Any» визначаємо як можливість підключати бекенди. Кожен бекенд явно описує свої можливості та обмеження; універсальний інтерфейс не означає автоматичної підтримки всієї Java на кожній платформі.

### 2. Використати наявні бібліотеки як фундамент

| Модуль | Запланована відповідальність |
|---|---|
| `jmouse-el` | Лексичні й синтаксичні контракти, вузли, відвідування, `SourceWriter`, `SourceLayout` |
| `jmouse-java-parser` | Повний синтаксичний AST Java |
| `jmouse-java-index` | Повторне використання придатних контрактів символів, classpath та пошуку декларацій |
| `jmouse-vm` | Компіляційна сесія, семантичний аналіз, досяжність, перетворення, контракти бекендів і підстановок |
| `jmouse-vm-typescript` | Семантика платформи TypeScript, цільовий AST, генератори, імена, імпорти, файли |
| Runtime та class library | Окремі артефакти з реалізаціями необхідної поведінки Java |

Важлива знахідка: `jmouse-java-parser` уже побудований на jME, має деклараційне дерево та режим читання виразів. Проте наявний `ExecutableBody` описує вирази, локальні зв’язування й посилання — це ще не повний AST виконуваних конструкцій, потрібний компілятору.

Тому план починається з аудиту й розвитку цього парсера. Другий Java-парсер усередині `jmouse-vm` створювати не варто.

### 3. Рекомендована стратегія парсингу

**Основний шлях — із Java source через власний парсер на jmouse-el.** Він краще відповідає вимогам читабельності: зберігає структуровані цикли, імена, коментарі та позиції.

План робіт:

1. Скласти матрицю покриття синтаксису Java за фактичною версією проєкту.
2. Доповнити дерево тіла методів: statements, expressions, області видимості, локальні й анонімні класи.
3. Відокремити синтаксичне читання від визначення типів і вибору перевантажених методів.
4. Зберігати походження кожного вузла для діагностики та source maps.
5. Для компіляції вимагати повного розбору потрібного коду: recovery парсера корисний редактору, але невідому конструкцію не можна мовчки пропускати під час генерації.

Для залежностей потрібно відразу розділити **читання сигнатур `.class`** і **трансляцію реалізацій із bytecode**. Наявність першого не дає другого. Якщо немає source, executable bytecode frontend або підстановки — компілятор має пояснити, якої реалізації бракує.

### 4. Побудувати граф захоплення коду від entry points

Залежності виконуваної програми утворюють **граф**, а Maven dependency tree лише допомагає знайти артефакти.

Пропонований алгоритм:

1. З конфігурації отримуємо entry points, exports і правила збереження.
2. Знаходимо декларації, їхні сигнатури та реалізації.
3. Аналізуємо виклики, доступ до полів, створення об’єктів та ініціалізацію класів.
4. Для віртуальних викликів додаємо можливі реалізації з урахуванням ієрархії та аналізу типів.
5. Враховуємо залежності, внесені runtime, підстановками й callback-контрактами.
6. Повторюємо аналіз до стабілізації.

Окремо моделюємо досяжність типу, інстанціювання типу, використання методу та необхідність ініціалізації класу.

Для reflection, `ServiceLoader` і зовнішніх викликів потрібні явні правила. Для кожного включеного символу зберігаємо пояснення: **«чому цей код потрапив у результат»**.

Такий поділ підтверджується архітектурою TeaVM: його аналізатор окремо відстежує класи, методи, поля й залежності, додані розширеннями. [DependencyAnalyzer](https://raw.githubusercontent.com/konsoletyper/teavm/master/core/src/main/java/org/teavm/dependency/DependencyAnalyzer.java)

### 5. Визначити семантичний конвеєр

```text
Sources + classpath + entry points
                ↓
             Java AST
                ↓
     Символи, типи, вибір викликів
                ↓
    Семантична модель програми
                ↕
    Досяжність + підстановки
                ↓
    Перетворення для платформи
                ↓
          TypeScript AST
                ↓
    jmouse-el SourceWriter
                ↓
     Файли + source maps + звіт
```

Перетворення, що додають виклики або runtime-компоненти, повинні повідомляти про нові залежності чи запускати повторний аналіз.

Зберігаємо високорівневу структуру програми настільки довго, наскільки можливо. Низькорівневе представлення потрібне там, де воно вирішує конкретне завдання; перетворення всього коду на машиноподібні інструкції ускладнить отримання читабельного TypeScript.

### 6. Для «бриджів» використати кілька точних понять

Одна абстракція `Bridge` змішає різні відповідальності.

| Поняття | Призначення |
|---|---|
| **Substitution** | Заміна Java-класу або члена іншою реалізацією |
| **Intrinsic** | Спеціальна компіляція конкретної операції чи виклику |
| **Interop binding** | Зв’язування з API цільової платформи |
| **Runtime component** | Підтримка поведінки Java під час виконання |

Кожна така реалізація має оголошувати не лише генерацію коду, а й залежності, підтримувані сигнатури, вимоги до платформи та семантичні обмеження.

Вибір підстановок повинен бути детермінованим. Конфлікт двох правил — діагностика з поясненням, а не випадковий переможець.

### 7. Зробити генератори адресними та замінними

Для TypeScript пропоную окремі компоненти за конструкціями, наприклад:

- `TypeScriptClassEmitter`
- `TypeScriptMethodEmitter`
- `TypeScriptInvocationEmitter`
- `TypeScriptTryStatementEmitter`

Це попередні назви, які уточнимо після проєктування контрактів.

Реєстрація має дозволяти знайти й замінити генератор конкретного виду вузла. Семантичні перетворення та форматування отримують окремі точки розширення.

Загальний обхід використовуємо з jME. Водночас генератору потрібен контроль порядку запису дочірніх конструкцій: звичайного обходу «батько, потім діти» недостатньо для дужок, пріоритетів операторів і блоків. Якщо спільного механізму бракує, розширюємо `jmouse-el`.

Стратегії генерації охоплюють імена, колізії, перевантаження, успадковані методи, експорти, імпорти, розкладку файлів і форматування. Імена прив’язуємо до ідентичності символів.

### 8. Окремо спроєктувати збереження семантики Java

До реалізації генераторів потрібні рішення щодо:

- `int`, `long`, переповнення, ділення, зсувів і `float`;
- рівності посилань, рядків, boxing та unboxing;
- масивів і перевірок типів;
- конструкторів, instance та static initialization;
- exceptions, `finally`, try-with-resources;
- інтерфейсів, default methods, lambdas і method references;
- reflection, потоків, моніторів та native API.

TypeScript-типізація сама по собі не забезпечить цієї поведінки. Для кожного пункту визначаємо: мовне перетворення, runtime, підстановка або явна непідтримуваність.

### 9. Аналіз TeaVM завершити картою фундаментальних вузлів

Поглиблений аналіз проведемо за відповідальностями:

| Вузол | Що визначаємо для jMouse |
|---|---|
| Frontend | Межу між завантаженням, парсингом і семантикою |
| Program model | Символи, ієрархію, виконувані тіла, походження |
| Dependency analysis | Досяжність, dispatch, залежності розширень |
| Linking | Перевірку повноти зібраної програми |
| Transformations | Контракти проходів, порядок і перевірку інваріантів |
| Backend | Можливості платформи, lowering та emission |
| Runtime / class library | Межу між компілятором і реалізаціями Java API |
| Naming / writing | Читабельність і стабільність результату |
| Diagnostics / cache | Пояснюваність і коректну інвалідацію |

У TeaVM вже видно поділ на dependency analysis, linking, transformations та emission, а JavaScript backend має окремі naming і writing компоненти. Це корисні архітектурні орієнтири; реалізацію та API jMouse проєктуємо самостійно. [TeaVM](https://raw.githubusercontent.com/konsoletyper/teavm/master/core/src/main/java/org/teavm/vm/TeaVM.java), [JavaScriptTarget](https://raw.githubusercontent.com/konsoletyper/teavm/master/core/src/main/java/org/teavm/backend/javascript/JavaScriptTarget.java)

### 10. Порядок виконання та критерії готовності

1. **Аудит основи:** карта можливостей і прогалин parser, index, jME та TeaVM.
2. **Архітектурний контракт:** модулі, модель програми, API розширень, порядок проходів.
3. **Frontend і семантика:** повноцінні тіла, символи, типи, виклики, діагностика.
4. **Граф програми:** досяжність, підстановки, runtime-залежності, пояснення включення.
5. **TypeScript backend:** lowering, цільове дерево, адресні генератори, імена та файли.
6. **Перевірка:** порівняння виконання Java і згенерованого коду, перевірка TypeScript, читабельності й детермінованості.
7. **Перевірка розширюваності:** сторонній генератор, підстановка та стратегія імен підключаються без зміни core.

Результатом проєктування мають бути конкретні контракти й приклади розширення. Саме вони покажуть, чи достатньо глибокі абстракції й чи справді зміни цільового коду обходяться без втручання в ядро.
